### C. Public Verification Key (`SPARKLE_PUBLIC_ED_KEY`) (WO-122-R4)
`SPARKLE_PUBLIC_ED_KEY` is the non-secret public 32-byte Ed25519 verification key matching `SUPublicEDKey` in the app's `Info.plist`.
To avoid secret-scoping friction while maintaining least-privilege, configure it as a **GitHub Actions Repository Variable**:
Navigate to **GitHub Repository Settings -> Secrets and variables -> Actions -> Variables -> New repository variable**:
- Name: `SPARKLE_PUBLIC_ED_KEY`
- Value: `<Base64-encoded 32-byte Ed25519 public key>`

| Config Name | Purpose & Format | Target Stage | Access Level |
| :--- | :--- | :--- | :--- |
| `SPARKLE_PUBLIC_ED_KEY` | Base64-encoded 32-byte Ed25519 public key matching `SUPublicEDKey` in the app bundle `Info.plist`. | Phase A, B, & C Verification | Public Configuration / Repository Variable (`vars.SPARKLE_PUBLIC_ED_KEY`) |

> [!NOTE]
> The release workflow (`.github/workflows/release-macos.yml`) evaluates `${{ vars.SPARKLE_PUBLIC_ED_KEY || secrets.SPARKLE_PUBLIC_ED_KEY }}` across all phases (Phase A, Phase B, Phase C) and fails closed if the key is missing, not valid Base64, or does not decode to exactly 32 bytes matching `SUPublicEDKey`. If an operator configures it as a Repository Secret instead, the pipeline supports both seamlessly without failure.

### D. Cryptographic Least-Privilege Isolation Architecture
The three-phase workflow strictly isolates secret access:
- **`unprivileged-qualification`**: Runs without environment bindings. Has zero access to environment secrets. Runs pure builds and 289 XCTests.
- **Phase A (`stage-draft` in `production-release`)**: The **only** job granted access to Developer ID, Notary API, and Sparkle private signing keys. Protected by human operator manual approval gate.
- **Phase B (`promote-public-feed` in `production-promotion`)**: Protected by separate human operator manual approval gate. Downloads staged draft assets, verifies CryptoKit Ed25519 signature against `SPARKLE_PUBLIC_ED_KEY`, mounts DMG read-only, checks notarization/stapling/Gatekeeper, and commits candidate feed to isolated branch. Cannot access any private signing keys.
- **Phase C (`verify-deployed-feed`)**: Read-only CDN curl verification. Zero secret access.

> [!CAUTION]
> **NEVER paste secret values into chat, issue threads, pull request comments, or Shared Cognitive Memory.**

## 4. Three-Phase Immutable Release Promotion & Feed Activation (WO-108, WO-115, WO-122-R1, WO-122-R2)
To eliminate collision errors, avoid re-signing verified binaries, and ensure immutable asset provenance, production releases follow a strict **Three-Phase Promotion** process with separated runner privileges:

### Phase A: Candidate Draft Staging (`release_phase: stage-draft`, WO-115, O1-G1A-01, O1-G1A-02, O1-G1A-03)
*Decoupled secret-free build in Phase 0 (unprivileged) and isolated signing in Phase A (`environment: production-release`).*

1. **Policy B Release Approval Record Prerequisite on Protected Main:**
   - Before triggering Phase A, an authenticated release approval manifest `docs/RELEASE_APPROVAL.json` must be committed and merged to `origin/main` via protected PR review.
   - The approval manifest binds the exact 40-character candidate commit SHA, release tag, version, and security attestation (confirming $0.00 spending limit and 12 blocked RPC methods).
   - If `docs/RELEASE_APPROVAL.json` is missing on `origin/main` or the target commit does not match `approved_commit_sha`, the workflow fails closed in `unprivileged-qualification`.

2. **Tag Candidate Commit:**
   ```bash
   git tag -s v1.0.0-build5 <reviewed-commit-sha> -m "Sentinel Node Wallet v1.0.0 (Build 5)"
   git push origin v1.0.0-build5
   ```

3. **Trigger Workflow Dispatch (Phase A):**
   - In GitHub Actions -> Select **macOS Production Release & Sparkle Deployment** -> **Run workflow**.
   - Input tag: `v1.0.0-build5`
   - Operator approval confirmed: `YES`
   - Release Phase: `stage-draft` (Phase A default).

4. **Automated Verification & Secret-Free Compilation (Phase 0):**
   - Unprivileged qualification verifies tag regex, build monotonicity (`build > 3`), and Policy B approval record on `origin/main`.
   - Runs full native unit test suite (`swift test`).
   - Verifies release broadcast lock (`VerifyReleaseBroadcastLock`).
   - Compiles release application bundle via `bash scripts/build_app.sh` (zero credentials).
   - Packages `dist/unsigned-app-bundle.tar.gz`, calculates SHA-256, and uploads it as a workflow artifact.
   - Exports immutable `verified_commit_sha` and `app_bundle_sha256`.

5. **Privileged Signing & Notarization (Phase A):**
   - Checks out repository at immutable `verified_commit_sha` (NOT a mutable tag).
   - Downloads `unsigned-app-bundle.tar.gz` and verifies SHA-256 matches Phase 0 manifest.
   - Extracts bundle safely into `dist/`.
   - Executes `bash scripts/build_production_dmg.sh --sign-only` (skipping compilation entirely while credentials exist in memory).
   - Signs DMG with Sparkle EdDSA key using `scripts/sign_appcast_enclosure.sh` with verified tool provenance.
   - Emits `RELEASE_ATTESTATION.json` binding `approved_commit_sha`.
   - Creates GitHub Release as a **Draft** via `gh release create --draft`.
   - Ephemeral keychain and Notary credentials are deleted.
   - **Result:** Immutable draft release staged; public feed on `main` remains untouched.

### Phase B: Owner Promotion & Candidate Feed Branch Staging (`release_phase: promote-feed`, WO-117, WO-118, WO-120, WO-121, WO-122-R1, WO-122-R2)
*Runs under unprivileged runner in GitHub environment `production-promotion` (with required operator reviewers) without code-signing certificates, Notary keys, or Sparkle private keys.*
1. **Operator Verification of Draft:**
   - Download draft DMG from GitHub Releases.
   - Verify Gatekeeper acceptance: `spctl -a -t exec -vv "/Volumes/.../Sentinel Node Wallet.app"` exits `0` with `accepted`.
   - Verify TeamIdentifier: `codesign -dv "/Volumes/.../Sentinel Node Wallet.app"` reports `TeamIdentifier=S8QMQZA656`.
   - Verify notarization ticket: `stapler validate Sentinel-Node-Wallet-*.dmg`.
2. **Trigger Workflow Dispatch (Phase B):**
   - Run workflow with `tag_name: v1.0.0-build5`, `operator_approval_confirmed: YES`, and `release_phase: promote-feed`.
   - Workflow runs in isolated `production-promotion` environment requiring owner sign-off.
   - **Step 0: Ensure Pinned Sparkle Artifacts Available (WO-120):**
     - Executes `swift package resolve` to populate pinned Sparkle 2.10.1 `sign_update` binary in `.build/artifacts/...` on disposable runners before any promotion logic runs.
   - **Step 1: Download & Attestation Verification (WO-117, WO-121):**
     - Downloads draft assets: DMG, `SHA256SUMS.txt`, `BUILD_MANIFEST.json`, `RELEASE_ATTESTATION.json`, `SPARKLE_ENCLOSURE.txt`.
     - Cross-checks `RELEASE_ATTESTATION.json` `commit_sha` against checked-out tag commit (`git rev-parse HEAD`), rejecting `github.sha` dispatch inconsistencies.
     - Validates `RELEASE_ATTESTATION.json` schema, matching SHA-256 and byte length.
     - Cryptographically validates Ed25519 signature against archive bytes using Swift CryptoKit (zero private key requirement).
     - Read-only mounts candidate DMG and verifies `Sentinel Node Wallet.app` `CFBundleIdentifier`, `CFBundleVersion`, `SUPublicEDKey`, `TeamIdentifier=S8QMQZA656`, Gatekeeper assessment (`spctl`), and notarization ticket (`stapler`).
   - **Step 2: Pre-Promotion Appcast Preflight Gating (WO-117, WO-120):**
     - Runs `publish_production_appcast.sh --preflight --prune-unsigned-legacy` against the downloaded archive to verify all live publish prerequisites and binary verifiers pass before making the release public.
   - **Step 3: Immutable Draft Release Promotion:**
     - Executes `gh release edit v1.0.0-build5 --draft=false` to promote the existing draft to public (**NO re-build, NO re-sign, NO asset collision**).
   - **Step 4: Staged Feed Branch Creation for Operator PR Review (WO-118, WO-122-R1, WO-122-R2):**
     - Because `main` is protected by mandatory pull request review and status checks, direct push to `origin/main` is strictly prohibited in production.
     - Phase B runs `publish_production_appcast.sh --stage-feed-branch --prune-unsigned-legacy` using the downloaded archive, signature, and public key.
     - Stages updated candidate `dist/appcast.xml` atomically onto an isolated branch `feed/${TAG}` via isolated git worktree against verified `origin/main` baseline, leaving `origin/main` untouched.
     - Outputs `STATUS: SIGNED_RELEASE_PUBLIC_FEED_PR_PENDING` with branch name, commit SHA, and blob SHA.
   - **Step 5: Output Release Status Summary (WO-122-R2):**
     - Generates GitHub Step Summary indicating the release is public and instructing the operator to review and merge the pull request for `feed/${TAG}` into `main`.

### Phase C: Post-Merge Live Deployed Feed Verification (`release_phase: verify-deployed`, WO-122-R2)
*Runs on an unprivileged runner post-merge to verify live CDN deployment fail-closed without modifying any assets.*
1. **Trigger Workflow Dispatch (Phase C):**
   - After merging the Pull Request from `feed/${TAG}` into `main`, dispatch workflow with `tag_name: v1.0.0-build5`, `operator_approval_confirmed: YES`, and `release_phase: verify-deployed`.
2. **Read-Only Finalizer Verification:**
   - Runs `publish_production_appcast.sh --verify-deployed-feed` (fail-closed, no `continue-on-error`).
   - Probes the public raw CDN feed URL on `origin/main`.
   - Performs bounded CDN readback requiring HTTP 200, exact-byte SHA-256 identity with candidate XML, ElementTree structural parsing of enclosure version/signature, and anti-trivial self-comparison guards.
   - If `main` has not yet been merged or CDN is stale, the finalizer outputs `STATUS: PUBLIC_RELEASE_AWAITING_FEED_APPROVAL` and fails closed (exit code 75).
   - Once the feed matches exact-byte identity on the CDN, the finalizer outputs `STATUS: DEPLOYED` and exits with code 0.

### Idempotent Feed Retry
If a network hiccup or CDN delay occurs after the release is public:
- Re-running Phase B (`release_phase: promote-feed`) detects that the release is already public, skips release mutation, and retries feed publication idempotently without touching binary release assets.

## 5. Authenticated Feed Contract & Legacy Migration (WO-113, WO-117, WO-118)
The feed publisher (`scripts/publish_production_appcast.sh`) enforces strict baseline authenticity:
1. **Remote Baseline First:** Baseline XML is derived directly from `origin/main:dist/appcast.xml`, preventing draft branch artifacts from polluting the production feed.
2. **Pruning Unsigned Legacy Items:** Historical Build 3 and Build 4 enclosures on `main` lack cryptographic signatures (`sparkle:edSignature`) and public keys (`SUPublicEDKey`). They were direct-download releases. When `--prune-unsigned-legacy` is specified during live publish, these items are pruned from the active update channel, ensuring that only cryptographically signed enclosures exist in the Sparkle feed. If unsigned enclosures are detected without `--prune-unsigned-legacy`, the publisher halts fail-closed with `FATAL INTEGRITY VIOLATION (WO-113)`.
3. **One-Time Manual Bootstrap Requirement:** Because Build 4 does not embed `SUPublicEDKey`, existing Build 4 installations **cannot** automatically update to Build 5 via Sparkle. Upgrading from Build 4 to Build 5+ requires a **one-time manual download / bootstrap**. Once Build 5+ is installed (embedding `SUPublicEDKey`), all subsequent updates (Build 5 -> 6, etc.) will perform authenticated automated OTA updates.
4. **Independent Read-Back & Typed Failure Modes:** Live publication reads back the raw GitHub CDN feed URL and validates HTTP 200 and matching candidate build/signature before exiting. If CDN readback fails, it reports `PARTIAL_RELEASE_FEED_NOT_LIVE` with diagnostic instructions.
