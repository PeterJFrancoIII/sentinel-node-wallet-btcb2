### D. Cryptographic Least-Privilege Isolation Architecture
The three-phase workflow strictly isolates secret access:
- **`unprivileged-qualification`**: Runs without environment bindings. Has zero access to environment secrets. Runs pure builds and 289 XCTests.
- **Phase A (`stage-draft` in `production-release`)**: The **only** job granted access to Developer ID, Notary API, and Sparkle private signing keys. Protected by human operator manual approval gate.
- **Phase B (`promote-public-feed` in `production-promotion`)**: Protected by separate human operator manual approval gate. Downloads staged draft assets, verifies CryptoKit Ed25519 signature against `SPARKLE_PUBLIC_ED_KEY`, mounts DMG read-only, checks notarization/stapling/Gatekeeper, and commits candidate feed to isolated branch. Cannot access any private signing keys.
- **Phase C (`verify-deployed-feed`)**: Read-only CDN curl verification. Zero secret access.

## 3. Trusted Signer Isolation Architecture (P0-G1B-R1-01)
The release workflow (`.github/workflows/release-macos.yml`) enforces strict cryptographic isolation between unprivileged candidate compilation and privileged signing:
1. **Unprivileged Qualification (Phase 0):**
   - Runs with zero secrets and zero environment bindings.
   - Checks out the candidate commit, compiles the application bundle, runs tests, and packages `dist/unsigned-app-bundle.tar.gz`.
   - Records the SHA-256 hash in workflow step outputs.
2. **Privileged Signing (Phase A):**
   - Runs in `production-release` environment with signing secrets.
   - **Checks out the reviewed release-control source revision on protected `main` (`${{ github.sha }}`)**, NEVER candidate code!
   - Asserts `github.ref == 'refs/heads/main'`.
   - Downloads `unsigned-app-bundle.tar.gz` and verifies SHA-256 matches Phase 0 output.
   - Inspects archive members before extraction (rejecting absolute paths, `..` traversals, and symlink escapes).
   - Executes trusted signing scripts (`scripts/build_production_dmg.sh --sign-only` and `scripts/sign_appcast_enclosure.sh`) loaded exclusively from the trusted `main` checkout.
   - Produces `dist/RELEASE_ATTESTATION.json` binding both `approved_commit_sha` (candidate) and `release_control_sha` (`main`).
   - Creates GitHub Draft Release targeting `approved_commit_sha`.

## 4. Release Pipeline Architecture & Fail-Closed Safeguards (R221)
On `main`, the release pipeline operates under strict fail-closed constraints:
1. **Three-Phase Release Workflow:**
   - **Phase A (`stage-draft`):** Unprivileged qualification, secret-free compilation, privileged signing/notarization, and staging of a GitHub Draft Release with cryptographically bound attestation.
   - **Phase B (`promote-feed`):** Gated by `production-promotion` environment, promotes verified draft release to public, preflights appcast generation, and stages candidate appcast to isolated `feed/${TAG}` branch for operator PR review.
   - **Phase C (`verify-deployed`):** Read-only verification of live CDN feed (`appcast.xml`), ensuring HTTP 200, exact version/build match, signature validation, and enclosure byte integrity.
2. **Mandatory Sparkle Tool Hash:** `SPARKLE_TOOL_HASH` must be explicitly provided via `vars.SPARKLE_SIGN_UPDATE_SHA256` matching a valid 64-char hex digest. Hardcoded fallback digests in workflow definitions are strictly prohibited.
3. **Policy B Immutable Approval Binding:**
   - `docs/RELEASE_APPROVAL.json` must exist on `origin/main` matching the exact candidate commit SHA, target tag, version, build number, and disarmed spending authority.
   - If `docs/RELEASE_APPROVAL.json` is missing or the target commit does not match `approved_commit_sha`, the workflow fails closed in `unprivileged-qualification`.

2. **Tag Candidate Commit:**
   ```bash
   git tag -s v1.0.0-build5 <reviewed-commit-sha> -m "Sentinel Node Wallet v1.0.0 (Build 5)"
   git push origin v1.0.0-build5
   ```

3. **Trigger Workflow Dispatch (Phase A):**
   - In GitHub Actions -> Select **macOS Production Release & Sparkle Deployment** -> **Run workflow**.
   - Input tag: `v1.0.0-build5`
   - Operator approval confirmed: `YES`
   - Release Phase: `stage-draft` (Phase A default).

4. **Automated Verification & Secret-Free Compilation (Phase 0):**
   - Unprivileged qualification verifies tag regex, build monotonicity (`build > 3`), and Policy B approval record on `origin/main`.
   - Runs full native unit test suite (`swift test`).
   - Verifies release broadcast lock (`VerifyReleaseBroadcastLock`).
   - Compiles release application bundle via `bash scripts/build_app.sh` (zero credentials).
   - Packages `dist/unsigned-app-bundle.tar.gz`, calculates SHA-256, and uploads it as a workflow artifact.
   - Exports immutable `verified_commit_sha` and `app_bundle_sha256`.

5. **Privileged Signing & Notarization (Phase A):**
   - Checks out repository at immutable `verified_commit_sha` (NOT a mutable tag).
   - Downloads `unsigned-app-bundle.tar.gz` and verifies SHA-256 matches Phase 0 manifest.

   - Creates GitHub Release as a **Draft** via `gh release create --draft`.
   - Ephemeral keychain and Notary credentials are deleted.
   - **Result:** Immutable draft release staged; public feed on `main` remains untouched.

## 5. Authenticated Feed Contract & Legacy Migration (WO-113, WO-117, WO-118)
The feed publisher (`scripts/publish_production_appcast.sh`) enforces strict baseline authenticity:
1. **Remote Baseline First:** Baseline XML is derived directly from `origin/main:dist/appcast.xml`, preventing draft branch artifacts from polluting the production feed.
2. **Pruning Unsigned Legacy Items:** Historical Build 3 and Build 4 enclosures on `main` lack cryptographic signatures (`sparkle:edSignature`) and public keys (`SUPublicEDKey`). They were direct-download releases. When `--prune-unsigned-legacy` is specified during live publish, these items are pruned from the active update channel, ensuring that only cryptographically signed enclosures exist in the Sparkle feed. If unsigned enclosures are detected without `--prune-unsigned-legacy`, the publisher halts fail-closed with `FATAL INTEGRITY VIOLATION (WO-113)`.
3. **One-Time Manual Bootstrap Requirement:** Because Build 4 does not embed `SUPublicEDKey`, existing Build 4 installations **cannot** automatically update to Build 5 via Sparkle. Upgrading from Build 4 to Build 5+ requires a **one-time manual download / bootstrap**. Once Build 5+ is installed (embedding `SUPublicEDKey`), all subsequent updates (Build 5 -> 6, etc.) will perform authenticated automated OTA updates.
4. **Independent Read-Back & Typed Failure Modes:** Live publication reads back the raw GitHub CDN feed URL and validates HTTP 200 and matching candidate build/signature before exiting. If CDN readback fails, it reports `PARTIAL_RELEASE_FEED_NOT_LIVE` with diagnostic instructions.
